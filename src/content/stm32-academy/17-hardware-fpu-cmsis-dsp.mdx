# Real-Time Schedulability (RMS/EDF) & Hardware FPU CMSIS-DSP Acceleration

## 1. Architectural Overview & Deterministic Schedulability

In mission-critical embedded systems (such as automotive braking, drone flight stabilization, and medical ventilators), an application is considered correct not only when its logical outputs are accurate, but **only when those outputs are delivered before strict temporal deadlines**.

A real-time operating system (RTOS) does not inherently make software "fast"; rather, it guarantees **predictability and determinism**. Before flashing multi-task firmware onto STM32 silicon, embedded architects must mathematically prove that the task set is schedulable under all worst-case conditions.

Furthermore, on ARM Cortex-M4F processors (such as the STM32F401RE), intensive mathematical tasks (e.g. digital filtering, Kalman state estimation, and FFT spectral analysis) leverage the **Hardware Floating Point Unit (FPU)**. Integrating the FPU into an RTOS requires balancing mathematical execution speed with context-switching stack overhead.

```
       +--------------------------------------------------------------+
       |               REAL-TIME SCHEDULABILITY SPECTRUM              |
       +--------------------------------------------------------------+
       | Paradigm         | Priority Assignment | Schedulability Bound|
       +------------------+---------------------+---------------------+
       | Rate Monotonic   | Static (1/Period)   | U <= n(2^(1/n) - 1) |
       | (RMS)            | Shorter T = High P  | Approaches 69.3%    |
       +------------------+---------------------+---------------------+
       | Earliest Deadline| Dynamic (1/Deadline)| U <= 100%           |
       | First (EDF)      | Closest D = High P  | Full Bus Saturation |
       +------------------+---------------------+---------------------+
```

## 2. Rate Monotonic Scheduling (RMS) & The Liu & Layland Bound

### 2.1 The Rate Monotonic Principle
Under **Rate Monotonic Scheduling (RMS)**, task priorities are assigned statically according to their request rates:
- A task with a shorter period `T_i` (higher repetition frequency) is assigned a **higher static priority**.
- A task with a longer period `T_i` is assigned a **lower static priority**.

RMS is mathematically proven to be the **optimal static-priority scheduling algorithm**: if any static-priority assignment can schedule a set of independent periodic tasks, RMS can schedule it.

### 2.2 The Liu & Layland Utilization Bound Theorem
For a system of `n` independent periodic preemptive tasks with deadlines equal to periods (`D_i = T_i`), Liu & Layland proved that the task set is **guaranteed schedulable** if the total CPU utilization `U` satisfies:

```latex
U = \sum_{i=1}^{n} \frac{C_i}{T_i} \le n(2^{1/n} - 1)
```

Where:
- `C_i`: Worst-case execution time (WCET) of Task `i`.
- `T_i`: Period (recurrence interval) of Task `i`.
- `n`: Total number of periodic tasks in the system.

#### Bound Convergence Matrix

| Number of Tasks (`n`) | Theoretical Utilization Bound (`U_max`) | Operational Guarantee |
| :--- | :--- | :--- |
| **`n = 1`** | `1 * (2^1 - 1) = 100.0%` | Fully schedulable up to 100% load |
| **`n = 2`** | `2 * (sqrt(2) - 1) ≈ 82.84%` | Guaranteed schedulable if `U <= 82.8%` |
| **`n = 3`** | `3 * (2^(1/3) - 1) ≈ 77.98%` | Guaranteed schedulable if `U <= 78.0%` |
| **`n = 4`** | `4 * (2^(1/4) - 1) ≈ 75.68%` | Guaranteed schedulable if `U <= 75.7%` |
| **`n = 5`** | `5 * (2^(1/5) - 1) ≈ 74.35%` | Guaranteed schedulable if `U <= 74.4%` |
| **`n -> ∞`** | `lim(n->∞) n(2^(1/n) - 1) = ln(2) ≈ 69.31%` | Universal asymptotic bound |

> **Key Takeaway:** If the total utilization of any arbitrary periodic task set is **under 69.3%**, it will **never miss a deadline** under Rate Monotonic Scheduling, regardless of task count or preemption frequency.

## 3. Response Time Analysis (RTA) for High-Utilization Systems

If total CPU utilization falls between 69.3% and 100% (`n(2^(1/n) - 1) < U <= 1.0`), the Liu & Layland test is **inconclusive**: the task set may still be completely schedulable!

To prove schedulability in this region, architects perform **Response Time Analysis (RTA)**:

```latex
R_i^{(k+1)} = C_i + \sum_{j \in hp(i)} \left\lceil \frac{R_i^{(k)}}{T_j} \right\rceil C_j
```

Where:
- `R_i`: Worst-case response time of Task `i` (including preemption from all higher-priority tasks).
- `hp(i)`: The set of tasks with priority higher than Task `i`.
- The equation is solved iteratively starting with `R_i(0) = C_i` until `R_i(k+1) = R_i(k)`.
- If `R_i <= D_i` for all tasks, the task set is proven **100% schedulable**.

## 4. Earliest Deadline First (EDF) Dynamic Scheduling

Under **Earliest Deadline First (EDF)**, task priorities are dynamic:
- At any scheduling decision point, the task whose absolute deadline is closest to the current time is granted the highest priority.
- **Optimality:** EDF is optimal among all scheduling algorithms on a single processor.
- **Utilization Bound:** Unlike RMS, EDF achieves a theoretical schedulability bound of **100%**:

```latex
U = \sum_{i=1}^{n} \frac{C_i}{T_i} \le 1.0
```

*Trade-off:* EDF introduces runtime overhead because the scheduler must re-evaluate and re-sort absolute deadlines dynamically upon each task arrival, whereas RMS uses fixed static priorities hardwired into FreeRTOS priority queues.

## 5. Cortex-M4F Hardware FPU Architecture & Lazy Stacking

The STM32F401RE features an **ARM Cortex-M4F** core equipped with a dedicated **FPv4-SP Single-Precision Floating Point Unit (FPU)**:
- 32 single-precision registers (`S0` through `S31`), accessible as 16 double-word registers (`D0` through `D15`).
- Floating-Point Status and Control Register (`FPSCR`).
- Hardware single-cycle multiply-accumulate (MAC), floating-point division, and square root instructions.

```
+-------------------------------------------------------------------------------+
|                       ARM CORTEX-M4F FPU REGISTER BANK                        |
+-------------------------------------------------------------------------------+
|  S0  |  S1  |  S2  |  S3  |  S4  |  S5  |  S6  |  S7  |  S8  |  S9  | S10 | S11 |
|-------------------------------------------------------------------------------|
| S12 | S13 | S14 | S15 | S16 | S17 | S18 | S19 | S20 | S21 | S22 | S23 | S24 | S25 |
|-------------------------------------------------------------------------------|
| S26 | S27 | S28 | S29 | S30 | S31 |  FPSCR (Status & Control Register)       |
+-------------------------------------------------------------------------------+
```

### 5.1 FPU Context Switching Overhead
A standard Cortex-M core saves 16 registers during a context switch (8 hardware auto-stacked + 8 software saved `R4-R11`), requiring **64 bytes** of stack.

If an RTOS naively saved the entire FPU register bank on every context switch:
- Saving `S0-S31` + `FPSCR` adds **33 additional 32-bit words (132 bytes)**!
- Every task stack would need an extra 132 bytes of RAM, and context-switch latency would jump from 12 cycles to over 50 cycles.

### 5.2 The Silicon Solution: Hardware Lazy Stacking (`FPCCR.LSPEN`)
The Cortex-M4F implements a hardware feature called **Lazy Stacking** (enabled by default via `FPCCR.LSPEN`):
1. When an interrupt occurs, the hardware automatically reserves 132 bytes of space on the task stack, but **does not write the FPU register contents to memory**.
2. If the preempting task (or ISR) does not execute any floating-point instructions, the FPU registers are left untouched. Upon returning, the space is simply un-reserved in a single cycle.
3. Only if the preempting task executes an FPU instruction does the hardware pause for 17 cycles to write `S0-S15` and `FPSCR` to memory.
4. **Result:** Tasks that perform simple logic or I/O pay **zero FPU context-switching penalty**.

## 6. Production-Grade Bare-Metal Implementation (C99)

The following production module initializes the **Hardware FPU**, verifies **Lazy Stacking**, and computes **Rate Monotonic Schedulability Analysis** at runtime.

```c
/**
 * @file    voltcore_fpu_schedulability.c
 * @brief   Hardware FPU Initialization & Rate Monotonic Schedulability Engine
 * @author  VoltCore Silicon Architecture Team
 */

#include <stdint.h>
#include <stdbool.h>
#include <math.h>

// System Control Block (SCB) Base
#define SCS_BASE            (0xE000E000UL)
#define SCB_CPACR           (*(volatile uint32_t *)(SCS_BASE + 0x0ED8UL))
#define FPU_FPCCR           (*(volatile uint32_t *)(SCS_BASE + 0x0F34UL))

/**
 * @brief Enable Cortex-M4F Hardware Floating Point Unit (Full Access)
 */
void fpu_hardware_init(void) {
    // CPACR (Coprocessor Access Control Register):
    // Bits [21:20] for CP10 (Single precision FPU)
    // Bits [23:22] for CP11 (Double precision / Extension)
    // Set bits [23:20] to 0b1111 (Full Access: 0xF << 20)
    SCB_CPACR |= (0xFUL << 20);

    // Memory pipeline synchronization barrier
    __asm__ volatile("dsb");
    __asm__ volatile("isb");

    // Enable Hardware Lazy Stacking in Floating-Point Context Control Register
    // Bit 31: ASPEN = 1 (Automatic FP context preservation)
    // Bit 30: LSPEN = 1 (Lazy context preservation enable)
    FPU_FPCCR |= (1UL << 31) | (1UL << 30);
}

// -----------------------------------------------------------------------------
// Rate Monotonic Schedulability Analysis Engine
// -----------------------------------------------------------------------------

typedef struct {
    const char *name;
    uint32_t wcet_us;   // Worst-Case Execution Time (C_i) in microseconds
    uint32_t period_us; // Period (T_i) in microseconds
} task_spec_t;

/**
 * @brief Calculate total system CPU utilization as a percentage
 */
float rms_calculate_utilization(const task_spec_t *tasks, uint32_t task_count) {
    float total_u = 0.0f;
    for (uint32_t i = 0; i < task_count; i++) {
        total_u += ((float)tasks[i].wcet_us / (float)tasks[i].period_us);
    }
    return total_u * 100.0f; // Return percentage (e.g. 68.5%)
}

/**
 * @brief Evaluate Liu & Layland Rate Monotonic Schedulability Bound
 * @return true if mathematically guaranteed schedulable, false if inconclusive
 */
bool rms_is_schedulable_guaranteed(const task_spec_t *tasks, uint32_t task_count) {
    if (task_count == 0) return true;

    // Calculate actual utilization: U = Sum(C_i / T_i)
    float actual_u = 0.0f;
    for (uint32_t i = 0; i < task_count; i++) {
        actual_u += ((float)tasks[i].wcet_us / (float)tasks[i].period_us);
    }

    // Calculate Liu & Layland Theoretical Bound: n * (2^(1/n) - 1)
    float n = (float)task_count;
    float bound = n * (powf(2.0f, 1.0f / n) - 1.0f);

    // If actual utilization <= bound, schedulability is 100% guaranteed
    return (actual_u <= bound);
}

// Example 3-Task Embedded Avionics Profile
static const task_spec_t g_avionics_tasks[3] = {
    { "IMU_Attitude_Filter",  200,   1000 },  // C1 = 0.2ms, T1 = 1.0ms (U1 = 20%)
    { "Motor_FOC_Current",    300,   2000 },  // C2 = 0.3ms, T2 = 2.0ms (U2 = 15%)
    { "Telemetry_Stream",    2000,  10000 }   // C3 = 2.0ms, T3 = 10.0ms (U3 = 20%)
    // Total Utilization = 20% + 15% + 20% = 55.0%
};

void run_schedulability_audit(void) {
    fpu_hardware_init();

    float utilization = rms_calculate_utilization(g_avionics_tasks, 3);
    bool guaranteed = rms_is_schedulable_guaranteed(g_avionics_tasks, 3);

    // Bound for n=3 is 77.98%. 55% <= 78% -> Guaranteed Schedulable!
    (void)utilization;
    (void)guaranteed;
}
```

## 7. Hardware-in-the-Loop Verification Protocol

To verify hardware FPU speedup and real-time execution bounds:

1. **FPU Acceleration Benchmark:**
   - Execute a 1024-point single-precision matrix dot product using soft-float emulation (with FPU disabled).
   - Enable hardware FPU via `SCB_CPACR` and re-run using hardware FPU assembly instructions (`VMUL.F32`, `VADD.F32`).
   - Measure execution cycles via the DWT Cycle Counter (`DWT_CYCCNT`).
   - **Expected Speedup:** Hardware FPU delivers between **14x and 18x speedup** compared to software IEEE-754 emulation.
2. **Schedulability Profiling via Logic Analyzer:**
   - Instrument Task 1 on **PA5**, Task 2 on **PA6**, and Task 3 on **PA7**.
   - Drive CPU load to 65% and capture continuous execution over 100,000 frames.
   - Verify on the timeline that zero deadline overruns occur, validating the Liu & Layland 69.3% guarantee.
